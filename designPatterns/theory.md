# 🧩 Design Patterns Overview — Categories, Descriptions, and Use Cases

| **Category** | **Purpose** | **Common Patterns & Descriptions** | **Typical Use Cases** |
|---------------|--------------|------------------------------------|------------------------|
| **Creational Patterns** | Manage **object creation** to make the system independent of how its objects are created and represented. | **Singleton** – Ensures a class has only one instance and provides a global point of access. <br> **Factory Method** – Defines an interface for creating objects, but lets subclasses decide which class to instantiate. <br> **Abstract Factory** – Provides an interface for creating families of related or dependent objects without specifying their concrete classes. <br> **Builder** – Separates object construction from its representation, allowing the same construction process to create different representations. <br> **Prototype** – Creates new objects by copying existing ones (cloning). | - Centralized configuration or resource managers (Singleton). <br> - Frameworks where object creation must be delegated (Factory Method). <br> - Cross-platform UI toolkits (Abstract Factory). <br> - Building complex objects step by step (Builder). <br> - Creating duplicates of objects with expensive initialization (Prototype). |
| **Structural Patterns** | Deal with **object composition** — how classes and objects combine to form larger structures. | **Adapter** – Converts one interface into another that clients expect. <br> **Bridge** – Separates abstraction from implementation so the two can vary independently. <br> **Composite** – Composes objects into tree structures to represent part–whole hierarchies. <br> **Decorator** – Dynamically adds new behavior to objects. <br> **Facade** – Provides a simplified interface to a complex subsystem. <br> **Flyweight** – Minimizes memory usage by sharing common parts of state between similar objects. <br> **Proxy** – Controls access to another object, adding a layer of abstraction. | - Integrating incompatible APIs (Adapter). <br> - Supporting multiple abstractions and implementations (Bridge). <br> - Managing hierarchical data (Composite). <br> - Adding features like logging or caching dynamically (Decorator). <br> - Simplifying complex libraries or frameworks (Facade). <br> - Managing large numbers of fine-grained objects efficiently (Flyweight). <br> - Adding access control, lazy loading, or remote access (Proxy). |
| **Behavioral Patterns** | Concerned with **communication and responsibility** among objects. | **Chain of Responsibility** – Passes a request along a chain of handlers until one processes it. <br> **Command** – Encapsulates a request as an object, allowing parameterization, queuing, or undo operations. <br> **Interpreter** – Defines a grammar and interpreter for a simple language. <br> **Iterator** – Provides a way to access elements of a collection without exposing its structure. <br> **Mediator** – Centralizes complex communications and control between related objects. <br> **Memento** – Captures and restores an object’s internal state without violating encapsulation. <br> **Observer** – Defines a one-to-many dependency between objects so when one changes state, others are notified. <br> **State** – Allows an object to change its behavior when its internal state changes. <br> **Strategy** – Defines a family of algorithms and makes them interchangeable at runtime. <br> **Template Method** – Defines the skeleton of an algorithm, allowing subclasses to redefine steps. <br> **Visitor** – Lets you define new operations on object structures without changing the classes. | - Event handling systems or middleware (Chain of Responsibility). <br> - Undoable commands or task queues (Command). <br> - Parsing or rule engines (Interpreter). <br> - Custom collection traversals (Iterator). <br> - UI dialogs managing multiple components (Mediator). <br> - Undo/redo functionality (Memento). <br> - GUI frameworks or reactive systems (Observer). <br> - Objects that alter behavior based on mode (State). <br> - Choosing algorithms at runtime (Strategy). <br> - Frameworks defining algorithms with customizable steps (Template Method). <br> - Applying operations to complex object structures (Visitor). |
